Cocos MCP 浏览器连接与信息获取·知识库
Cocos MCP 浏览器连接与信息获取 · 知识库
面向读者：需要理解或扩展 Cocos MCP「浏览器调试」能力的开发者。
路径基准：本文所有相对路径均以项目根目录 cocos_mcp/ 为基准；行号基于写入时的源码，重构后请以符号名为准。
覆盖范围：src/**、browser-companion/**、docs/** 中与「连接浏览器」和「从浏览器获取信息」相关的全部实现。
0. 先建立心智模型：这套系统到底在干什么
一句话概括：MCP 通过三条可选的「管道」接进浏览器页面，然后用一套统一的工具对页面做「读状态 / 收事件 / 发输入 / 录性能」，最后把证据有界、脱敏地回传给 AI。
打个比方：
你（AI）坐在控制台前，想观察并操纵远处房间（浏览器页面）里的一台机器（Cocos 游戏）。
you 不能直接伸手进去，得选一根「线」接过去。这里有三根线，接口一样，插哪根都能用同一套遥控器：
Creator GameView 线：机器就在隔壁房间（Creator 编辑器内部的 GameView），走的是 Electron 的内部通道，插上就能用，零配置。
Chrome CDP 线：机器在一台独立的 Chrome 里，走的是 Chrome 标准调试协议（CDP）。要么自己新开一个带调试端口的 Chrome，要么用 CDP Bridge 扩展接管一个已经打开的普通 Chrome。
Companion 线：老版本的专用扩展通道，保留给还没迁移的用户。
三根线在代码里叫 transport，取值分别是 creator-gameview / chrome-cdp / chrome-companion。上层工具不关心你插的是哪根，因为有一个「路由器」把统一的调用转发给当前生效的那根线。
理解这一点后，剩下的细节都是围绕两个问题展开：
怎么接线（连接 / 接管 / 切换 / 断线恢复）—— 对应第 3、4 部分。
接上以后能拿到什么（页面状态、DOM、console、异常、网络、截图、WebGL、性能 trace）—— 对应第 8 部分。

为什么要分这么多层？
L3 的「端口（Port）」就是一份契约：上层只知道「我能调 click()、read()」，不知道底层是 Electron 的 sendInputEvent 还是 CDP 的 Input.dispatchMouseEvent。
L4 的「路由器（Router）」持有三个实现，同一个时刻只让一个生效（active）。切换通路 = 换 active，上层代码一行不用改。
这样加一条新通路时，只要实现同一个端口接口、在 container 里注册进去即可，不用动任何工具代码。

2.2 src/access/mcp/tool-schema.ts（26 行）

5.3 重试与恢复（connectWithRecovery，:134-172）
端口集合 = 去重([input.port ?? 9220, 9220])
循环 attempt = 0..3（RETRY_DELAYS = [200, 500, 1000] ms）：
  ├─ 对每个 port 调 cdp.list(port)，汇总 latestTargets + targetPorts(id→port)
  ├─ select(latestTargets) 选目标；original ??= selected（锁定首次选择）
  ├─ orderedCandidates(...) 排候选
  ├─ 逐候选：
  │    ├─ companion: 固定用 9220；其余用 targetPorts 或 input.port
  │    ├─ cdp.connect(port, id)
  │    ├─ activateMonitoring（按 status.transport 切到对应 monitor）
  │    └─ 成功即返回
  └─ 无 target 且无候选 → NOT_FOUND
全部失败 → recoveryError（汇总 relayAvailable、availableChannels、最近 3 个错误）
recoveryError（:116-126）：如果 relayAvailable===false，提示「CDP Bridge 9221 relay 不可用」；否则提示「已刷新页面目标并完成 3 次恢复尝试」。
防串扰：beginOperation/isCurrent（:23-32）用 WeakMap 记录连接代次（revision），异步连接完成时若代次已变则放弃，避免旧连接覆盖新连接。

9.4 端口 9221 relay / CDP 隧道机制（重点）
[扩展 CDP Bridge] --ws--> ws://127.0.0.1:9221/plugin   (config.js 被改写)
                              |
                  [cdp-tunnel proxy-server.js, PORT=9221]
                              |
      对外暴露 9220 标准 CDP 端点(/json/version → /devtools/browser/...)
      及 9221 的 /client、/json/browsers 端点
                              |
[MCP chrome-remote-interface]
    discoverChromePages(9220): CDP.List + Tab.getMuteStatus
    → connectTunnelPage(9220, targetId):
        CDP.Version → browser socket → Target.attachToTarget(flatten)
        失败回退 ws://127.0.0.1:9221/client
    → createCdpPageSession → transport = "chrome-cdp"
关键点：扩展自身不暴露 CDP，而是作为「插件」连到 relay；relay 把多个 Chrome 标签伪装成标准 CDP browser/target 端点，MCP 用普通 chrome-remote-interface 即可接管已经打开、未带调试参数的 Chrome。这与旧 Companion（扩展直连 MCP WS、MCP 发命令给 chrome.debugger）在架构上完全不同。
端口冲突处理：setup 脚本检测 9220/9221 被占用时，验证是否是可复用 relay（GET /json/browsers），否则停止并提示，不强杀。
端口一览：
8765（可配置到 8785）：MCP HTTP 服务 + Companion WS（共用）。
8766：旧 Companion 更新服务。
8768：CDP Bridge 本地更新服务。
9220：CDP Bridge relay 暴露的标准 CDP 端点（默认接管端口）。
9221：CDP relay 内部端口（/plugin 扩展接入、/client 接管回退）。
9222：launch 新开 Chrome 的起始调试端口；browser_monitor start 零配置扫描端口。

11. 排错与自查清单
11.1 接管已打开网页失败
按 docs/CHROME_MONITOR.md:30 的顺序：
确认已安装且启用唯一的 CDP Bridge 扩展（扩展 ID hcbkmdhlajamkfdjcbokidiamdjgffid）；旧 Companion 不需要同时装。
确认 9221 relay 正在运行——setup-browser-bridge.cmd 启动的 cdp-tunnel/server/proxy-server.js。状态里 relayAvailable:false 就是它挂了。
保持目标标签页打开，且是 HTTP(S) 页面。
先 browser_connect list 扫描，看目标是否出现；多个页面时用完整 URL 或 targetId 指定。
browser_connect adopt（可带 url）→ status 确认 transport: "chrome-cdp"。
Chrome 显示「正在被调试」是 chrome.debugger 的系统行为，正常。
托管策略安装出现「浏览器由组织管理」是正常的，不要用「加载已解压扩展」。
11.2 定位界面报错
browser_monitor start，记下返回的 nextCursor；
在页面中只复现一次问题；
browser_monitor snapshot 传入起始游标；
异常和 Promise rejection 会返回 message/stack/url/line/column，console 事件保留有限参数。这样能区分本次复现的错误和接管前历史日志。
11.3 版本信息不变
Companion 握手会上报 protocolVersion / extensionVersion / capabilities。更新扩展后若版本信息没变，说明 Chrome 仍用旧 Service Worker——去 chrome://extensions 刷新扩展，或等企业策略更新完成。

11.5 互斥与限制
browser-monitor-electron 与源码断点调试器 debugger-electron 互斥占用同一 debugger。
性能追踪不支持 GameView，只支持 chrome-cdp / chrome-companion。
browser_interact 不提供脚本执行/刷新/导航/localStorage 修改——不要指望它做这些。
帧间隔分析需要至少 3 个可归属的实际呈现事件，不能从 rAF / 截图数 / 设置 FPS 推断。
堆快照、保留路径、完整内存泄漏分析要继续用 Chrome DevTools MCP。
